# pdfcn adoption research for Growth OS

Date: 2026-10-01. Planning only; no dependencies installed or application code changed. Primary repository inspected at commit `39c75c1abbbad7b89ad1d8d3ea740ef635818a4b` (commit date 2026-09-24). APIs below are source-verified; deployment compatibility remains untested.

## Verified upstream facts

- pdfcn is a copy-owned React component registry with Takumi and Forme rendering bases. It is not a drop-in PDF styling package or a reason to migrate Growth OS to Next.js. [Repository](https://github.com/shadcn-labs/pdfcn)
- Components are installed through shadcn, e.g. `npx shadcn@latest add @pdfcn/forme/text`. Registry dependencies include renderer and theme utilities. Use this as documented syntax, not the final reproducible production installation command: pin/review component source and lock dependencies during implementation. [Installation source](https://github.com/shadcn-labs/pdfcn/blob/main/apps/web/content/docs/%28root%29/installation.mdx)
- The inspected documentation app uses React 19.2.5, Forme core/react `^0.25.0`, and `takumi-pdf ^0.11.0`. Those are upstream versions, not a validated compatibility matrix for our React 19.0.1/TypeScript 5.8/Vite 6 app. [Package manifest](https://github.com/shadcn-labs/pdfcn/blob/main/apps/web/package.json)
- Forme's example server API explicitly calls `serialize(<Demo />)` from `@formepdf/react`, then `renderPdf(JSON.stringify(document))` from `@formepdf/core`. Its comment warns that dynamically importing a different serializer instance can discard nested pages. Takumi's example imports `render` from `takumi-pdf/next`; copying that route directly into Express is inappropriate. [Forme route](https://github.com/shadcn-labs/pdfcn/blob/main/apps/web/app/api/pdf/forme/route.tsx), [Takumi route](https://github.com/shadcn-labs/pdfcn/blob/main/apps/web/app/api/pdf/takumi/route.tsx)
- The theme schema supplies semantic colors, fonts, spacing, margins, page size, and orientation. Some comments still describe react-pdf even though the current rendering bases differ: actual renderer behavior must be tested. [Theme definitions](https://github.com/shadcn-labs/pdfcn/blob/main/apps/web/registry/types/pdf-themes.ts)
- **Concurrency review required:** Forme's `PdfcnThemeProvider` stores theme in mutable module-level `serializedTheme`. This is a concrete isolation concern, not proof of a reproduced leak. Adopt request-isolated rendering or refactor owned components to explicit theme propagation, with two-brand concurrent tests. [Provider source](https://github.com/shadcn-labs/pdfcn/blob/main/apps/web/registry/bases/forme/components/theme-provider.tsx)
- **Sample content must be removed:** the marketing block defaults to sample metrics and names, passes a fixed positive status, and hardcodes a blue chart. Copying it unchanged would reproduce the current truthfulness and branding defects. [Marketing block](https://github.com/shadcn-labs/pdfcn/blob/main/apps/web/registry/bases/forme/blocks/report-marketing/report-marketing.tsx)
- MIT license requires preservation of copyright/license notice. The GitHub releases API returned an empty release list during inspection; this and pre-1.0 renderer versions justify pinned source and an acceptance spike, not a blanket claim that the library is production-ready. [License](https://github.com/shadcn-labs/pdfcn/blob/main/LICENSE), [Releases API](https://api.github.com/repos/shadcn-labs/pdfcn/releases)

## Existing seams and defects verified locally

- `src/pages/Reports.tsx:151`: `handleExportSummaryPDF` passes template KPIs plus hardcoded channels, attribution narratives, and a fixed tenant name to the exporter. Styling alone cannot make this report valid.
- `src/services/exportService.ts:465`: `toExecutiveSummaryPDF` hand-positions jsPDF content, hardcodes amber `#F59E0B` and a dark background, and prints an unconditional verification claim.
- `src/services/exportService.ts:64`: generic `toPDF` captures a DOM canvas. This is a separate export path and should not be silently confused with the structured executive report.
- `src/lib/palette.ts`: current core brand is orange `#FF481B`, black and white, with semantic status colors. Shared approved logo assets and tenant brand settings must inform PDF design, rather than adopting pdfcn's sample palette.

## Proposed integration, not existing capability

1. First define a server-owned, versioned `ReportSnapshot` containing workspace, report period, metric provenance, assumptions, claim/evidence IDs, tasks, approvals, delivery receipts, outcomes, and commercial scope. Validate input using the existing Zod boundary and workspace membership enforcement. Reject unexplained synthetic values; unknowns remain unknown.
2. Implement a narrow `renderExecutiveReport(snapshot, brandProfile)` adapter using owned pdfcn Forme components. Prototype Forme first because its documented serialize/render boundary fits Express without importing Next. Verify fonts/native or WASM packaging on the actual deployment target before selecting it permanently; if it fails, evaluate pdfcn's Takumi base using that renderer's supported Node API.
3. Assemble a client-ready report: executive decision, evidenced revenue gaps, recommended solutions, milestones and duration, deliverables, fees and assumptions, work completed, how delivered, execution log, outcome measurement, evidence appendix. Report section selection and client branding should follow validated user requirements. The referenced social post's exact deliverable logic must be verified separately before attributing this structure to it.
4. Replace the executive PDF button's local data assembly with a call for a saved report snapshot and authenticated PDF artifact. Proposed endpoint names and storage design are implementation choices, not existing APIs. Persist report/version/template/brand versions, content hash, generated timestamp and artifact ID. Preserve a separate browser-download event: generated, download initiated, downloaded (when verifiable), and delivered must mean different things.
5. Keep renderer code out of the Vite client bundle. Use bounded server rendering, timeouts, safe image/font assets, restricted outbound fetching, workspace-scoped artifact access, sanitized filenames and protected evidence URLs. These are application controls; pdfcn does not establish them for us.

## Acceptance spike and tests

- Render representative A4 reports with the actual Sigma logo and orange palette; inspect every page at print resolution. Confirm text extraction, links, margins, chart labels, long titles, table continuation, page numbers, missing data, 100+ rows, long evidence citations, currency formats, and licensed embedded fonts. Test Arabic/RTL only if included in selected client requirements; do not promise it untested.
- Run two workspaces with different themes/data concurrently and repeat sequentially; neither data nor styles may cross scopes. Tamper with artifact IDs to verify isolation.
- Assert every factual metric/claim references the report snapshot, calculation or evidence; no hardcoded success, sample marketing metrics, fake scan counts, or unconditional verification language.
- Verify the deployed build can render using its actual Node runtime and memory limits. Test render errors, timeouts, retries and duplicate clicks without duplicate final artifacts.
- Browser tests must inspect the downloaded file's name, PDF signature, nonzero size, extracted expected content and rendered appearance. A success toast alone is insufficient evidence. An artifact supplied by the user does establish that an earlier download occurred; update the stress-test finding accordingly.

Decision: adopt pdfcn through a bounded, pinned-source proof-of-fit and brand acceptance gate, then replace the executive report renderer. Truthful report data and delivery evidence are prerequisite workstreams, not properties supplied by the PDF library.
